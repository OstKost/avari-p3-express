# Агентная разработка Avari

Пути навыков и рекомендации по компактным инструкциям сверены с [документацией Codex по skills](https://developers.openai.com/codex/skills/) и [AGENTS.md](https://developers.openai.com/codex/guides/agents-md/). Проверка новой установки должна проходить в чистой папке и новой сессии. Локальная статическая проверка подтверждает структуру и ссылки, но сама по себе не доказывает обнаружение пользовательским клиентом кастомных ролей.

Harness — это связка контекста, повторяемых рабочих процедур, ограниченных ролей, исполняемых проверок и доказательств результата. Он хранится в репозитории и помогает продолжать работу в новом чате без повторного исследования проекта.

Настройка ориентирована на Codex. Форматы сверены 24 сентября 2026 с официальными [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [skills](https://learn.chatgpt.com/docs/build-skills) и [subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents). Инструкции навыков создания использованы для разделения областей, коротких триггеров и явных результатов; актуальные пути Codex выбраны по документации. Старые `.cursor`-форматы не дублируются.

## Быстрый старт

Нужны Python 3.11+ (только standard library), Go, Node.js и pnpm. Версии Go/Node/pnpm в CI видны в [workflow](../.github/workflows/ci.yml). Установить зависимости web через `pnpm install --frozen-lockfile` в `apps/web`. Автоматическая установка пакетов при запуске проверок не выполняется; Go может скачать модули обычным механизмом Go.

```sh
make context
make check-harness
make check
```

Открыть новый чат в корне проекта, чтобы перечитались AGENTS/config. Для проверки discovery попросить: «Перечисли активные инструкции, локальные avari-скилы и доступные роли; ничего не меняй». Codex умеет обнаруживать skills при обновлении; если они не появились, перезапустить сессию. Файлы ролей и project config требуют поддержки установленным клиентом и доверия к проекту. Статическая проверка не доказывает, что конкретная сессия загрузила их.

Если кастомная роль не поддерживается клиентом, её TOML содержит читаемые инструкции: основной агент может передать их обычному worker или выполнить работу последовательно. Глобальные настройки моделей, разрешений и MCP этим harness не меняются.

## Состав

- [AGENTS.md](../AGENTS.md): короткий постоянный контекст, цикл работы, маршрутизация и критерии завершения.
- [API](../apps/api/AGENTS.md), [Web](../apps/web/AGENTS.md), [specs](../_init/AGENTS.md): правила, применимые к конкретной области. Root явно требует читать их при входе в область, поскольку старт из корня не гарантирует автоматическую загрузку всех вложенных файлов.
- [.agents/skills](../.agents/skills): `avari-plan`, `avari-feature`, `avari-debug`, `avari-verify`. Метаданные помогают выбрать процедуру, полный текст читается по необходимости.
- [.codex/agents](../.codex/agents): explorer собирает факты, api и web реализуют выделенные срезы, reviewer независимо ищет ошибки. Координатор — основной агент, отдельная роль для него не нужна.
- [.codex/config.toml](../.codex/config.toml): максимум два дочерних агента одновременно; модели наследуются из пользовательской сессии. Встроенный лимит среды может быть строже.
- [scripts/harness.py](../scripts/harness.py): единые команды для локальной работы и CI, компактный вывод, полные логи и машинно читаемый итог.
- [Карта](architecture.md), [приёмка](verification.md), [шаблон задачи](tasks/TEMPLATE.md), [ADR](decisions/TEMPLATE.md), [PR template](../.github/pull_request_template.md): память и evidence по необходимости.

## Как работать каждый день

**Небольшое исправление.** Дать конкретную проблему и ожидаемый результат. Один агент изучает нужный код, исправляет, запускает целевую проверку. План-файл, ADR и команда агентов здесь обычно избыточны.

> Используй $avari-debug. Исправь [наблюдаемую ошибку]. Воспроизведение: […]. Ожидаю […]. Добавь проверку регрессии, если она оправдана, и выполни проверки затронутой области.

**Новая функция.** Указать пользовательское поведение, границы и приёмку. Для изменения API+UI согласовать контракт до параллельной реализации. Передать api/web непересекающиеся файлы; интеграция и общая конфигурация остаются у основного агента.

> Используй $avari-feature. Реализуй [функцию]. Приёмка: […]. Ограничения: […]. Для существенного изменения используй независимого avari-reviewer; исправь подтверждённые проблемы и покажи evidence.

**Планирование среза P3.express / SDLC.** Использовать спецификации `_init/` и каноническое руководство P3.express v2 для формирования задач.

> Используй $avari-plan. Спланируй срез функциональности. Сопоставь требования с кодом, выдели решения о данных и маршрутах, приёмку и порядок работ. Сейчас только план.

**Продолжение в новом чате.** Для долгой работы сохранить короткую задачу в `docs/tasks/<slug>.md`: что сделано, что проверено, что осталось и следующий шаг. Запрос: «Продолжи задачу из …». Не копировать всю историю диалога.

**Финальный контроль.** `avari-verify` выбирает область, выполняет проверки и честно описывает пробелы. Root требует независимого reviewer для существенного изменения, когда доступны субагенты; для мелких правок достаточно одного агента и целевых проверок.

## Проверки

- `make check-api`: `gofmt -l` без изменения исходников, `go vet`, `go test -race -cover`, production build с `CGO_ENABLED=0`.
- `make check-web`: ESLint и `tsc -b && vite build`. Это не component/E2E тесты.
- `make check-harness`: TOML, простой локальный формат skill metadata, уникальность имён, локальные Markdown-ссылки, размеры инструкций и поведение runner.
- `make check`: все перечисленные gates. После исправления ошибки достаточно повторить затронутые проверки, если интеграционный риск не изменился.

`.harness/runs/<scope>-<unique>/` содержит отдельные логи и `summary.json`. Успех выводится одной строкой на команду; при ошибке — последние 40 строк и путь к полному логу. Отсутствующий инструмент и ненулевой exit code дают failure. Вывод `gofmt` тоже считается ошибкой. Лимит одной команды — 10 минут; на macOS/Linux при timeout или Ctrl+C runner завершает созданную им группу процессов, включая дочерние тесты/сборку. На Windows очистка дерева процессов не гарантируется; целевые среды этого harness — macOS и Linux CI. Набор проверок не выбирается автоматически по `git diff`: явная область избегает пропусков новых и cross-layer файлов.

CI запускает те же Make targets в отдельных jobs, сохраняет логи при ошибке на 7 дней и отменяет устаревший запуск той же ветки. Изменение workflow действует после публикации в GitHub; локальный pass не означает успешный hosted CI. Python-validator проверяет принятый здесь простой формат, а не всю спецификацию YAML/Codex. Он не проверяет доступность внешних ссылок.

Hooks на каждое действие не добавлены: они бы повторно запускали проверки и увеличивали задержку. Повторяемый контроль находится в Make/CI. Branch protection на стороне GitHub не включена автоматически: чтобы gate блокировал merge, владелец репозитория должен назначить соответствующие checks обязательными. Инструкции и reviewer не являются sandbox-защитой; реальные разрешения определяет клиент. Даже read-only defaults роли могут быть переопределены параметрами родительской сессии.

## Где экономятся токены

1. В постоянном контексте — короткая карта и решения, влияющие на работу. Детали API, UI и процедур загружаются только для подходящей задачи. Это использует [progressive disclosure skills](https://learn.chatgpt.com/docs/build-skills).
2. `make context` выдаёт карту и ограниченный список Git-изменений без чтения всех specs, картинок, lockfiles или содержимого окружения.
3. Детерминированный скрипт не нужно генерировать заново. Успешные длинные логи не попадают в диалог; при ошибке можно открыть нужный фрагмент.
4. Task file заменяет пересказ длинного чата. ADR предотвращает повторное обсуждение уже принятого решения.
5. Субагент возвращает небольшой результат со ссылками. Это уменьшает шум в контексте координатора, однако его собственные входные и выходные токены тоже расходуются. Официальная документация прямо предупреждает о [повышенном общем расходе при использовании субагентов](https://learn.chatgpt.com/docs/agent-configuration/subagents).

Нет честного заранее известного процента экономии: здесь не проводился A/B benchmark. Оценивать нужно по сопоставимым задачам — общее usage всех агентов, время до принятого результата, число повторных циклов и найденные после завершения дефекты. Дешёвый запуск с неверным результатом может оказаться дороже качественного.

Более экономную модель разумно выбирать для чёткой локальной проверки, сильную — для неопределённой архитектуры, миграций и сложных ошибок. Модели намеренно не закреплены в репозитории: их доступность и поддерживаемые reasoning settings зависят от сессии. Не снижать их вслепую ради цены отдельного вызова.

## Польза и цена подхода

Плюсы: быстрый вход в репозиторий, меньше путаницы между spec и кодом, воспроизводимые gates, короткая передача контекста, независимая проверка крупных изменений и понятные доказательства для портфолио. Показать решение, тесты и ограничения убедительнее, чем заявлять «production-grade» без измерений.

Минусы: инструкции надо поддерживать при изменении архитектуры; дополнительные агенты расходуют токены и требуют координации; ручной Go/TS-контракт может разойтись; passing build не ловит ошибки взаимодействий. Слишком много правил начинает мешать. Поэтому бюджеты ограничивают размер root/scoped/skill файлов; это проектная конвенция, её можно обоснованно изменить вместе с валидатором.

Автоматического E2E, performance/security audit, деплоя, внешнего task tracker или MCP-зависимостей этот набор не устанавливает. Добавлять их стоит под реальный сценарий. Для следующего существенного UI-среза полезен один browser smoke test, затем расширение по риску. Перед публичным релизом отдельно согласовать версии toolchain между локальной средой, CI и Docker.

## Как поддерживать

После повторяющейся ошибки сначала улучшить проверку или ближайшее правило; новый skill нужен только для отдельного повторяемого workflow. Устаревшие инструкции удалять. Не превращать task files в ежедневный журнал и не хранить в них полные tool logs. Завершённые задачи сохранять как evidence при наличии пользы для команды/портфолио.

При изменении команд, структуры, skill или agent выполнить `make check-harness` и проверить соответствующий сценарий в новой сессии. Статическая валидация и несколько тестовых заданий дополняют друг друга.
