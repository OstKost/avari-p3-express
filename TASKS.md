## Общий контракт API v1

База: `/api/v1/p3`. Все записи принадлежат одному локальному рабочему пространству. JSON в `snake_case`, ID — строки, даты — `YYYY-MM-DD`, время события — RFC3339. Ошибки: `{ "error": "..." }`, 400 за ввод, 404 за отсутствующий объект, 500 за серверную ошибку. Пустые коллекции — `[]`.

- `GET /projects` → `{ "data": ProjectSummary[] }`; `POST /projects` с `{name, description?, due_date?}` → `Project` и 201; `GET /projects/{id}` → `Project` с `phases`, `sdlc_stages`, `blockers`, `actions`, `activity`; `PATCH /projects/{id}` с полями проекта, включая `archived`, `rag_status`, `progress`, `current_phase`, → `Project`.
- `Project` включает `id`, `name`, `description`, `due_date`, `archived`, `rag_status`, `progress`, `current_phase`, `phases`, `sdlc_stages`, `blockers`, `actions`, `activity`. `ProjectSummary` — те же основные поля плюс `current_sdlc_stage`, `open_blockers`.
- `Phase`: `id`, `code`, `name`, `description`, `progress`, `due_date`, `status`, `steps`. `Step`: `id`, `code`, `name`, `description`, `status`, `due_date`, `progress`, `checklist`, `links`, `comments`, `blockers`. Шаги и фазы создаются при создании проекта из канонического шаблона P3.express v2. `PATCH /steps/{id}` меняет `status`, `due_date`.
- `POST /steps/{id}/checklist` с `{text}` → пункт; `PATCH /checklist/{id}` с `{text?, done?}` → пункт; `DELETE /checklist/{id}` → 204.
- `POST /steps/{id}/links` с `{title,url,description?}` → ссылка; `DELETE /links/{id}` → 204. `POST /steps/{id}/comments` с `{text}` → комментарий.
- `POST /projects/{id}/blockers` с `{title,description?,step_id?,sdlc_stage_id?}` → блокер; `PATCH /blockers/{id}` с `{resolved}` → блокер.
- `PATCH /sdlc-stages/{id}` с `{status?,progress?,start_date?,due_date?}` → стадия.
- `GET /actions` → `{data: Action[]}`; `POST /actions` с `{project_id,title,due_date?,priority?,step_id?}` → действие; `PATCH /actions/{id}` с `{title?,due_date?,priority?,done?}` → действие. `Action`: `id`, `project_id`, `step_id`, `title`, `due_date`, `priority`, `done`.
- `GET /articles` → `{data: Article[]}`; `POST /articles` с `{title,category,summary?,body}` → статья; `PATCH /articles/{id}` → статья. Статические справочники P3.express/SDLC могут жить в UI, собственные статьи — в SQLite.
- `POST /projects/{id}/cycles/{phase_code}` → новое выполнение для повторяемой группы B/C/D/E; прошлое остаётся в истории. `GET /projects/{id}/cycles` → `{data: Cycle[]}` с кодом, номером и временем.

Операции изменения инвалидируют запросы проекта, списка проектов, действий и активности. Шаг без пунктов имеет 0%; прогресс фазы — среднее по шагам активного цикла. RAG и прогресс проекта вводятся вручную. Пустой срок — `null`. Валидация URL допускает только http/https.

## Порядок и проверка

1. API и UI идут параллельно по контракту выше. Не редактировать чужие области; API владеет `apps/api/**`, Web владеет `apps/web/**`, координатор — общими файлами и интеграцией.
2. Координатор проверяет договорённости и устраняет расхождения. Ошибки новых сценариев исправлять в ответственном слое, не ослабляя проверки.
3. Проверить `make check`, сценарий с временной БД и в браузере: проект → шаг → чеклист → перезагрузка; блокер → Главная; действия → Мои задачи; SDLC независимо от P3; архивирование; повторный цикл.

## Наблюдения и решения

- Макеты иллюстрируют визуальный язык; их подписи A–G о стадиях разработки противоречат отдельной модели SDLC. Используется каноническая P3.express v2.
- Версия 1 — один пользователь без входа. Публикация и многопользовательская работа требуют отдельного решения.
- Собственные данные хранятся локально в SQLite. Внешние URL остаются ссылками, без синхронизации с Jira/GitLab.

## Фактические проверки

- `make check`: 8/8 (harness, gofmt, vet, race tests, Go build, ESLint, TypeScript, Vite build).
- HTTP smoke на свежей временной SQLite базе, порт 4822, миграции до версии 5: POST проекта вернул 201, создал 7 фаз, 33 шага и 8 начальных событий без шума от 33 шаблонных пунктов. Два отмеченных пункта дали прогресс шага 100% и добавили ровно 3 события (создание/две отметки). Созданы блокер и статья; статья отредактирована; повтор цикла B получил номер 2, в коллекции 8 записей (начальные циклы A-G и второй B).
- Браузерный сценарий Web-агента: создание проекта, навигация по фазе и шагу, сохранение чеклиста после перезагрузки, блокер на Главной, закрытие диалога клавишей Escape.
- Дополнительно: Chromium снимок главной страницы на viewport 375×812 после загрузки данных; проверено, что карточки, приоритетные блоки и навигация отображаются без горизонтального переполнения.
- Не весь маршрут продукта повторно проходился вручную в браузере: SDLC, фильтры, архивирование и задачи покрыты сборкой/типами и API, но для них не записан отдельный end-to-end браузерный сценарий.
- Независимый review выявил риск неатомарной истории и URL-валидации; добавлена транзакционная запись событий через триггер и ужесточена проверка HTTP(S) URL, включая пустой/недопустимый порт. Патч чужой сущности проверяется через `FindProjectFor`; модель активности фронтенда уже использует `description`.
- Контракт циклов уточнён по фактической форме `GET /cycles`: `{data: Cycle[]}`; UI-адаптер согласован с ней. Существующий старый сервер на порту 4820 не останавливался; интеграционная проверка шла на изолированных 4812/4822 и временной базе `/tmp`.

## Решённые ограничения v1

- Личное локальное рабочее пространство без аутентификации; не публиковать API в общий доступ до отдельного решения по доступу.
- Jira/GitLab и другая внешняя синхронизация отсутствуют по требованию; URL хранятся как ссылки.
- Данные приёмочного smoke лежат только во временной базе `/tmp/avari-p3-final-20260925.sqlite`; данные приложения пользователя не затрагивались.
